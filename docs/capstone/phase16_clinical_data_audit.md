### 2.5 Docker Volume — Production Runtime Upload Path

`docker-compose.yml` defines a named Docker volume `uploads_data` mounted into two services:

```yaml
# ai-service (line 233)

# celery-worker (line 288)
- uploads_data:/app/uploads

# Volume declaration (line 338)
volumes:
  uploads_data:
```

- `UPLOAD_DIR` setting defaults to `"uploads"` (relative path, resolved to `/app/uploads` inside the container).
- PDFs uploaded via the `POST /api/ai/trials/upload` endpoint are stored in this volume.
- The volume is **not seeded** by the repository — it starts empty on every fresh `docker-compose up`.

**Implication:** No clinical trial PDFs are pre-seeded for Docker. Any PDFs ingested during a demo session live only in the named Docker volume `medmatch_uploads_data` on the host machine running Docker.

### 2.7 Production API — Trial PDF Upload Endpoint

The production AI-service exposes:

```
POST /api/ai/trials/upload    (upload_trial_pdf)
GET  /api/ai/trials/upload/status/{task_id}
```

- Accepts `.pdf` files only (`ALLOWED_UPLOAD_EXTENSIONS: [".pdf"]`).
- Validates PDF magic bytes (`%PDF-`), file size (`MAX_UPLOAD_SIZE_MB`), and page count.
- Saves with a UUID-randomized filename (`{uuid4()}.pdf`) under `UPLOAD_DIR`.
- Queues async Celery task for text extraction → Gemini LLM structured extraction → database ingestion.
- **No demo/seed clinical trial PDFs are bundled.** Upload is purely a runtime user action.

## 3. Patient Medical Record PDF Documents

### 3.1 Current Working Tree — On-Disk State

**Result: ZERO patient medical record PDF files exist anywhere in the current working tree.**

The patient data pathway works differently from clinical trial PDFs:

- **Patient notes** are submitted via `POST /api/ai/patients/{patient_id}/notes` as **JSON body text** (a `PatientNoteCreate` schema), not as PDF file uploads.
- The `PatientNoteService` accepts pre-extracted clinical note text (plain string), generates an embedding, and stores it in the database.
- **There is no PDF upload endpoint for patient medical records.** There is no `save_pdf` call in any patient-related service.

**There is no PDF-based patient record ingestion pipeline in the current production codebase.**

### 3.2 Patient Fixture Data — `data/fixtures/patients.json`

The repository contains `data/fixtures/patients.json` with **6 synthetic patient records** (`SYN_P001`–`SYN_P006`):

| Field | Value |

| Identity fields | Synthetic IDs (`SYN_P001` etc.) — no real names, DOBs, addresses, MRNs |
| Clinical content | Fabricated oncology profiles (lung cancer, NSCLC, specific biomarkers like EGFR Exon 19 del, KRAS G12C) |
| `clinical_note` field | Free-text synthetic SOAP/oncology note strings embedded directly in JSON |
| File format | JSON (not PDF) |

No patient data is stored as a PDF. Patient clinical notes are **structured JSON text** in the fixture and **plain text strings** at runtime via the API.
